# Review and scope of the additive 841 work

Base: `main` at `e55726c6a7cfa6265229fa2a29aa789df16cabf6`.

The repository's stated goal is a larger, explicitly verified kissing
configuration, primarily in dimension 13. This work addresses two concrete
engineering gaps: batching the existing 841 calibration protocol and certifying
finite-decimal direction files with exact integer arithmetic. It does not claim
a new kissing-number lower bound or an independent recovery of the known 841.

## Why these tasks

- PR #3 is merged. Its opt-in faithful CPU solver, initialization rules,
  35,000-update schedule, and separate decimal-Gram polish handoff already
  exist. Reimplementing another unconstrained numerical search would not
  resolve the missing calibration. The new engine is an opt-in extension and
  is checked against the unchanged C implementation.
- PR #4 already proposes CI. This branch does not duplicate it or edit any
  existing workflow.
- PR #5 contains exact reconstructions of known PackingStar 1,146-point
  configurations. PR #9 contains the audit rejecting the claimed Steiner
  switch family and an exhaustive check of its specified norm-16 integer
  augmentation family. Those branches are not merged into this work, and
  their searches are not repeated.
- The published 841-point decimal coordinate fixture has a positive margin.
  It can therefore be checked directly as normalized rational directions;
  fitting every coordinate to a single quadratic field is unnecessary.

Four Luna agents were assigned the kernel, checkpointed runner, independent
C parity harness, and exact decimal verifier. Their work was isolated in
separate local worktrees. Accepted files are additions under `experimental/`;
existing solver sources, certificates, results, and defaults are unchanged.

## Boundaries on interpreting earlier results

Some headings in the existing `kissing/README.md` are stronger than the evidence
immediately beneath them. A finite collection of numerical hole-search starts
does not prove global maximality. Single-point jamming does not prove collective
jamming or optimality. Counting equations versus unknowns is not by itself a
proof that every larger structured family is impossible. Exact finite-family
exhaustions should be read with their stated family restrictions. These
observations are why this work preserves earlier material and makes no new
impossibility claim from an unsuccessful numerical search.

## Independent baseline checks

The unchanged `test_faithful_841.py` passed, including its decimal-Gram handoff,
bounded polish, learning-rate, and non-finite-state regressions.

A separate parent-agent check parsed every published coordinate with
`fractions.Fraction`, scaled all rows by a common denominator of `10^22`, and
tested every pair with Python integers. For nonzero integer directions `u,v`,
write `p = u.v`, `q = u.u`, `r = v.v`. Their normalized inner product is at most
one half exactly when `p <= 0` or `4*p*p <= q*r`. Squaring is applied only in
the positive case. The normalized directions are explicit real unit vectors
in the original ambient dimension.

For `lib/testdata/authors_841_coordinates.txt`:

- SHA-256: `883943a52b35fbb314417a61050507f8ad7ee2c3466ef4ea70441837114c8ab0`.
- Shape: 841 rows, 12 coordinates, all nonzero.
- All 353,220 unordered pairs checked.
- 177,081 nonpositive inner products; 176,139 positive inner products strictly
  below one half; no equalities or violations.

This independently verifies the existing published example. It neither finds a
new configuration nor satisfies the repository's independent-search
calibration gate.

## Source and validation limits

The published search script was also read at Git blob
`2a3e8ce119c20ddc3aedf00f44f8600ad91d8e23` in
[`k-nic/841_in_12D`](https://github.com/k-nic/841_in_12D/blob/main/search_841_riesz.py).
Its batch mean, persistent within-macro Adam moments, fresh macro state, and
schedule agree with the intended extension. The current C solver and upstream
autograd have different derivatives where the pair-distance clamp is active;
the new kernel documents that boundary explicitly. C parity is not a claim of
bitwise equivalence to upstream CUDA execution.

Validation here uses CPU float64. CUDA execution, 512-candidate device memory
usage, full discovery-scale campaigns, and independent recovery of 841 remain
unvalidated unless a later result explicitly supplies that evidence.

## Integration review

The parent review required corrections to the initial kernel's large
`B * pair_count * dimension` temporary, the runner's learning-rate constants
and final-macro accounting, the initial split-file checkpoint design, and a
comparison helper that could overlook NaNs. These corrections were made only
in new experimental files.

Validation after integration:

- 10 exact certificate tests, including decimal perturbations that binary
  float would round onto the one-half boundary.
- 7 kernel tests, including independent finite differences and batch scaling.
- 8 runner tests covering initialization, resume equality, corrupted state,
  output-path collisions, interrupted atomic replacement, and stage/macro/end
  transitions. Lifecycle boundary tests use a small test-only schedule;
  they do not constitute a full 35,000-update search.
- The C parity suite invokes the unchanged `adam_raw_stage`, comparing raw
  coordinates, gradients, and moments across separated stages, including
  `s=40000`. It also checks two updates with all 841 points, the active
  distance-clamp convention, B=2 scaling, and the runner's schedule/view.
- An additional parent comparison against the actual upstream PyTorch script
  on B=3, N=20, d=12 matched nine updates across s=8, 16, 40000 to maximum
  coordinate difference `3.33e-16` after the memory refactor.
- The existing decimal-Gram preparer was run on the published fixture. The
  newly written reconstructed coordinate file also passed the exact integer
  verifier strictly for all 353,220 pairs.

All reported timings are bounded CPU probes, not GPU performance estimates.

An integration smoke run also used the real canonical 840-point core with
four independent hypercube extras (`--batch-size 4 --seed 51`). It completed
the first 1,000-update stage, saved a checkpoint at macro 0/stage 1/update 0,
and resumed to update 1,001 with Adam step 1,001 retained. Independent readback
gave best maximum inner products `0.6107835424131238` and
`0.5937793199197225`, respectively. Both are infeasible and both outputs are
labelled diagnostic. This validates a real-shape stage-boundary continuation;
it is not calibration recovery and is not an estimate of the final schedule's
performance.
